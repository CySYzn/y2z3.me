Scenario: BookWorld, an online bookstore, has a SOC alert for an unusual spike in database queries and server resource usage — a sign of possible malicious activity against customer data and internal systems. As lead analyst, the task is to work from the network traffic to identify the attack vector, assess the scope of any data breach, and determine whether the attacker gained further access.
SQL injection shows up in a capture as SQL syntax inside URL query strings — quotes, comment markers, UNION SELECT — URL-encoded on the wire (%27 = ', %20 = space). Automated tools like sqlmap add their own fingerprints, such as a sqlmap/… User-Agent and hex-encoded marker strings. CyberChef's URL Decode turns the encoded payloads back into readable queries.
Q1By knowing the attacker's IP, we can analyze all logs and actions related to that IP and determine the extent of the attack, the duration of the attack, and the techniques used. Can you provide the attacker's IP?
Statistics → Conversations → IPv4. 111.224.250.131 ↔ 73.124.22.98 dominates with 88,484 packets / 29 MB over roughly 1,497 seconds; the other external client (170.40.150.126) sent just 256 packets / 39 kB of ordinary book searches.
answer111.224.250.131
Q2If the geographical origin of an IP address is known to be from a region that has no business or expected traffic with our network, this can be an indicator of a targeted attack. Can you determine the origin city of the attacker?
An IP2Location lookup places 111.224.250.131 in Shijiazhuang, Hebei, China (ISP: ChinaNet Hebei Province Network, ASN 4134). Geolocation is approximate — the lookup itself warns coordinates sit near a population center — so treat it as a triage signal, not attribution.
answerShijiazhuang
Q3Identifying the exploited script allows security teams to understand exactly which vulnerability was used in the attack. This knowledge is critical for finding the appropriate patch or workaround to close the security gap and prevent future exploitation. Can you provide the vulnerable PHP script name?
http and ip.addr == 111.224.250.131
Every attacker request targets /search.php with SQL stuffed into the search parameter, including error-based payloads (EXTRACTVALUE, CAST) that provoke runs of 500 Internal Server Error responses.
answersearch.php
Q4Establishing the timeline of an attack, starting from the initial exploitation attempt, what is the complete request URI of the first SQLi attempt by the attacker? Note: Decode the Value.
http contains "search.php"
The legitimate client (170.40.150.126) searches titles; the attacker starts with test test, war, book, then a lone book%27 quote at 12:03:31 — the classic "does it break the query" probe. The first complete injected payload is book%20and%201=1;%20--%20- at 12:03:52, immediately followed by a 1=2 variant: a true/false pair. Decoded in CyberChef, it gives the answer.
answer/search.php?search=book and 1=1; -- -
Q5Can you provide the complete request URI that was used to read the web server's available databases? Note: Decode the Value.
tcp.stream eq 151 (packet bytes, string: INFORMATION_SCHEMA)
Searching packet bytes for INFORMATION_SCHEMA finds the request that lists schemas. The stream's User-Agent is sqlmap/1.8.3#stable, and the hex constants wrapping the output (0x7178766271, 0x7a76676a636b, 0x7176706a71) decode to qxvbq, zvgjck, qvpjq — sqlmap's random delimiters, which reappear in the response to mark where the stolen data starts and ends.
answer/search.php?search=book' UNION ALL SELECT NULL,CONCAT(0x7178766271,JSON_ARRAYAGG(CONCAT_WS(0x7a76676a636b,schema_name)),0x7176706a71) FROM INFORMATION_SCHEMA.SCHEMATA-- -
Q6Assessing the impact of the breach and data access is crucial, including the potential harm to the organization's reputation. What's the table name containing the website users data?
tcp.stream eq 154
The same UNION technique against INFORMATION_SCHEMA.TABLES; the response body contains ["admin", "books", "customers"] between sqlmap's markers. Three tables, and customers holds the user data.
answercustomers
Q7The website directories hidden from the public could serve as an unauthorized access point or contain sensitive functionalities not intended for public access. Can you provide the name of the directory discovered by the attacker?
http.request.method == "POST"
The POST list shows repeated submissions to /admin/login.php — a path the public site never links to — and later a POST to /admin/index.php. Shortly beforehand, a burst of GETs for alphabetical PHP names (/zones.php, /zoom.php, /zope.php…) is consistent with automated content discovery.
answer/admin/
Q8Knowing which credentials were used allows us to determine the extent of account compromise. What are the credentials used by the attacker for logging in?
tcp.stream eq 647
After several earlier attempts against the same form, the login in this stream posts username=admin&password=admin123%21 (Content-Length 35) and gets a 302 Found followed by an authenticated GET /admin/index.php. %21 URL-decodes to !, so the password is admin123! — a weak, guessable credential.
answeradmin:admin123!
Q9We need to determine if the attacker gained further access or control of our web server. What's the name of the malicious script uploaded by the attacker?
http contains ".php"
A POST /admin/index.php (1,122 bytes, application/x-php) at 12:24:18 delivers the file, and the next request is GET /admin/uploads/Nvri2vhp.php — the attacker calling their own script. Note the random-looking filename.
answerNvri2vhp.php

Lessons learned: The root cause is unsanitized input in search.php — parameterized queries close the hole outright. For detection, quotes, UNION, INFORMATION_SCHEMA, a sqlmap User-Agent, and bursts of 500 responses are all cheap, high-signal alerts. The follow-on damage came from weak spots around the flaw: an unprotected /admin/ panel, a guessable admin123! password, and an upload path that accepted PHP. Restrict admin panels by IP or VPN with MFA, disable script execution in upload directories, and keep the application's database account least-privileged.
